## 研究输入统一配置，不按因素与指标拆成两个必经步骤

因素与指标的科学用途有区别，不要求界面分成两个库、两份定义或两个必经步骤。建议沿用“输入与建模关系”统一采用系统定义，再按用途显示配置；土壤水分既可作为某个模型的因素，也可作为另一个研究的目标，不能按角色复制指标身份。

- 观测量继续从系统输入目录采用准确定义、单位、科学尺度、来源和方法。X/Y及其他用途按实际节点合同解释，普通研究不另设自定义指标入口。
- 灌溉处理表达人为安排的处理条件，土壤水分表达观测或估计的量；品种分组表达比较或分层规则。这些区别决定条件校验，不是拆分页面的理由。处理或分组确有需要时，在统一列表中展开水平、对照或字典引用等额外配置；普通研究不强制填写。
- 当前输入目录未完整登记截图中的处理和分组定义。统一入口是交互与目录演进方向，不表示现有目录已经包含这些组件，也不因为VariableRole支持treatment/group就宣称相关执行已打通。
- 处理或分组定义需采用已登记定义或受管字典；实际地块、样方/点位、作物及分组分配仍在具体研究中绑定。统一选择不取消来源与资格边界。

本轮将该原则写入两份本地对接说明，不改动模型、输入合同或截图所属业务前端。

## 02/03编辑表单与处理水平、对照的核对

用户补充“编辑因素·灌溉处理”和“处理水平与对照”两张截图。本轮只核对配置资格，不新增处理或分组合同，不改变运行逻辑。

处理水平是某个试验因素的不同设定；例如同一灌溉试验可将常规灌溉规则登记为CK，另两种预先约定的灌溉规则登记为T1/T2。编码本身没有剂量、大小顺序或通用农业含义，对照不必是不灌水。对照组用于比较处理效果，不是训练/验证/测试集。未填写处理信息不能自动视为CK；同一对象多天记录不自动成为独立试验重复。

截图字段的当前支持边界：

| 截图内容 | 当前合同事实与交互结论 |
| --- | --- |
| 名称、编码、取值类型、单位 | 系统输入目录固定，普通研究不可直接覆盖；角色用途与科学定义分别处理。不是把已有指标改名或改成类别就能创建新处理组件。 |
| 输入/目标或研究用途 | 可按准确模型与来源配置，不改科学身份。treatment/group枚举存在，不等于有完整试验设计与效应估计能力。 |
| 适用层级与样方继承 | 输入来源固定unit_kind；ScientificUnit支持层级与experimental_unit_ref，validate_context核对处理分配一致性。没有截图全部继承/分配策略的通用配置入口，不能任意改来源尺度。 |
| CK/T1/T2水平 | Variable.categories可表达类别代码，当前65项系统输入均为number，没有完整登记截图处理与分组定义；不能据类别字段存在声称普通目录已支持。 |
| 对照标记、水平显示名称、实际处理量与单位 | 当前没有相应完整的处理水平合同。仅categories或角色不足以保存这些科学含义。实际量应有方法、单位和执行记录，不能只写“每次登记”却任意改变处理规则。 |
| 缺失处理策略 | 截图枚举没有对应通用研究配置字段。运行中的待采集状态与某种已登记的缺失处理算法不是同一能力。 |
| 重复观测隔离 | 已有试验单位引用、holdout_unit_refs和split_unit等基础约定，不等于所有来源/模型都支持截图所示自动分组隔离策略；必须在训练与评价环节按真实记录检验。 |

建议业务UI沿用统一“输入与输出”：系统指标定义只读，提供按合同允许的来源属性、采集要求及模型输入/预测输出配置。处理与对照只在确实开展处理效应研究，且处理定义、水平、对照、实际分配和分析方法合同完整登记后按需提供；当前不应开放无合同约束的自由编辑并宣称保存有效。合同合法但执行制品/来源未接通的组件仍可按既有规则设计保存，不能把这一原则扩大成允许未定义字段。

本轮通过当前虚拟环境和FastAPI TestClient调用POST /designer/validate：system-study原配置valid=true；修改第一个系统指标name或unit均valid=false，分别定位variables/0/name、variables/0/unit；修改unit_kind为quadrat返回invalid_source，定位collection_requirements/0/unit_kind。读取目录确认value_type为number的条目65项，Variable字段中没有对照、实际剂量、分配方式或缺失策略字段。无数据库、调度和代码修改。

## 只读指标详情及本期移除处理对照的范围判断

用户进一步要求系统指标完全不可编辑，仅查看详情。03目录HTTP200已实测包含名称、编码、版本、描述、类型、单位、范围、观测尺度、具体来源、数值性质、方法及接入状态；业务UI可复用目录条目构造只读详情，不需要另加详情API。当前卡片仅摘要，不据此声称已有独立详情弹窗。

本轮另用system-study将lai.minimum改为0.1，通过POST /designer/validate实测valid=true。validate_input_bindings仍允许在目录范围内收紧minimum/maximum，是严格只读要求的实际缺口。不能只禁用表单就宣称后端全部拒绝定义编辑，也不能直接破坏旧方案合法收紧范围的解释与运行。后续需在新采用/新编辑边界收口，并验证历史原样导入、回读、运行及未改定义的更新，不混同方案质量规则与指标定义。

架构与本期业务判断：当前产品围绕标准输入、基础模型组合、训练预测和成果复用，处理水平/对照不是必需环节，应从当前业务UI移除，不为其新增通用试验设计框架。它对未来比较灌溉/施肥等处理效果有独立价值，届时应有明确试验业务、真实分配及合适分析方法，再采用完整版本化组件合同。现存treatment/group/assignments等结构保留历史兼容与扩展能力，不因本期不展示就删除。此判断基于业务边界，不仅是因为当前尚未实现。

本轮仅同步本地设计和前端对接说明，未修改源代码或生产界面。严格禁止范围改写的实现问题已单独记录。

## 截图中需要特别确认的组合

当前株高来源包括height_cm（点位）和plant_height（单株），单位均为cm；没有现成的“样方平均株高”来源。目录的唯一quadrat输入为商品果产量，执行状态明确为待适配。

因此“玉米＋样方×观测日期＋同日指标估计＋样方平均株高”尚不能作为已经完整支持的配置验收。需确认样方均值是按固定规程人工采集，还是对多株/多点观测聚合；后者须保留样方成员、时间、缺测和聚合方法，而不是把field_ref改成样方名。

| 主要输出 | 必须明确目标指标与真实成果，但不限于单个目标。 | 不作为基本信息项。目标指标在“指标定义与用途”维护；成果类型、质量与发布信息在末分区维护。确需主次排序时引用已有指标或输出，不重复定义名称、单位与公式。 |

第一分区按用户最终决定仅保留方案名称、负责人、研究目标、模板版本四项。观测粒度随指标来源与装配规则确认，目标指标在指标分区维护，任务与成果在计算、评价和输出分区确定。实际作物不在本区选择。草稿允许暂缺，正式检查与启动分别执行相应完整性规则。

对截图示例，系统需表达“同日水分条件估计样方平均株高”的任务，不能把“分析水分关系”自动认定为因果效应；若只采用观察数据的回归，应按估计或关联解释。样方日观测可以有多行，但同一样方的重复日期不自动成为多个独立试验单元，评价划分须防止同对象或未来信息泄漏。

每项科学事实只维护一次：目标指标及单位由指标引用确定；粒度由明确的数据合同与转换规则确定；版本由准确引用确定；负责人由业务成员关联确定。前端可以多处展示同一事实，但不能产生第二份可独立修改的配置。

## 用户确认的方案与实例边界

用户进一步明确：保存可复用研究方案之后，再发起具体研究，此时填写地块、样方点、作物和周期。此约定取代上一轮将作物范围作为基本信息可选填写项的建议。

- 方案定义指标与角色、来源合同、计算连接、观测尺度和对齐要求、采集与评价规则，不要求真实地块、点位、实际作物和日历起止日期。
- 研究实例绑定准确方案版本，填写并核验实际地块、样方/点位、作物、周期及当次来源取数范围；实际启动前检查来源、执行制品、数据与时间条件。
- 例如方案可要求“单株株高”，发起研究再选实际植株/点位；方案可要求连续30天日数据，发起研究再确定具体日期。来源合同在设计阶段仍须明确，来源选择器若依赖实际对象与日期，其具体范围在实例绑定时补齐。
- 当前合同中仍有sampling_selection、具体日期参数等历史设计能力，不能据本次约定声称所有API已完整实现两阶段分离。实施时需逐入口检查并保留历史配置解释，不在本轮分析中直接更改公开协议。

三个字段的选择项均应由本系统的合同或目录约束，但不必各增加一个独立目录接口。研究任务目前没有统一“同日估计/未来预测”选项合同，不能将objective/purpose枚举直接当作该下拉；观测尺度已有03指标目录的unit_kind，但没有完整的跨来源相容候选查询；目标指标来自03指标目录，成果来自06准确模型的输出端口，二者不可混成一个静态枚举。只有一个合法值时展示说明，多值时提供选择，无法相容时给出明确缺口。

## 三项定义与后续指标、模型选择的联动

三项定义均须参与同一份方案的约束，自动汇总展示不意味着取消校验；不建议先增加三个独立表单值，再维护另一份指标、模型和输出状态。

- 研究任务影响组件能力、取数时点、训练与评价方式。未来预测要求输入在预测起点可获得；分析或拟合成果不能自动当作可再次调用的预测模型。任务不直接唯一决定算法。
- 观测尺度影响装配和模型输入。不同来源尺度不必完全相同，但须有明确的空间对应、时间对齐、聚合或上下文映射；如单株株高可以与其所属地块当日天气配对，不能一律要求天气也是单株采集。不同尺度的任意直接拼接不可接受。
- 目标指标影响可采用的模型及标签与成果绑定；数值目标与类别目标要求不同，多目标研究可采用支持多目标的模型或显式拆为多个模型。“预测表/模型文件”等成果类型与目标指标分别解释，成果显示排序不应无故改变因素选择。
- 交互应双向校验：先选目标、因素或模型均可，模板给出默认值；每次改变只标记受影响的绑定，给出具体原因与可行调整，不静默删除用户选择。缺少来源取数或执行制品与数学组合冲突分开，前者允许按既有规则保留设计并阻止实际运行。

现有compile_plan/check_definition已检查准确端口、请求Schema、来源定义和指标用途等部分合同；这不等于已经实现三个新控件驱动的完整候选联动，尤其统一任务时点和跨尺度转换仍有缺口。本轮只记录规则，不修改API和前端。

## 是否必须在开始设置：架构判断

结论是不把研究方式、样本单位、主要输出设成第一步的三个独立必选项。它们影响合法组合，不足以证明它们必须在选择指标和模型之前填写。当前架构以准确指标来源、组件请求、端口绑定与图输出为配置依据，更适合在各自的权威配置环节确定，再对整份方案校验。

1. 研究意图可以先表达，但保留ResearchPlan.objective/purpose的现有含义；同日估计/未来预测不能直接冒充这两个字段。串联图可包含拟合、生成特征与训练等不同操作，不能用全局下拉替代每个节点的请求合同。必要的预测时间规则在设计完成前明确，不用算法名称自动猜测意图。
2. CollectionRequirement.unit_kind随每项指标来源定义。土层、地块天气、卫星覆盖区可以各有尺度，再通过显式适配进入模型。开头新增一个全局sample_unit并据此覆盖或排除来源，会误伤合法组合。
3. 目标指标在指标用途配置中决定；模型成果由Composition.outputs引用实际节点端口。尚未选模型时，真实成果端口通常尚不存在，不应提前建立另一份primary_output定义。多目标、分支和中间产物继续由图表达。
4. 草稿合同允许未完成定义，正式保存重复执行完整设计检查；阶段先后应与此区分。取消首页的强制选择不删除既有科学规则，也不表示新增任务时点、跨尺度适配已实现。

## 分步验证的实际边界

当前wizard.canLeave只在页面检查基础信息及计算节点存在，普通下一步不调用API；04独立核对来源采用，method-picker应用模型时及wizard.check调用页面专用/designer/validate，业务接口10复用完整设计检查，11/12保存重复验证。06/08提供合同和兼容候选，不是完整验证。09允许未完成草稿，不可当作研究合法性检查。

本轮实际HTTP核对：仅提供name、question、responsible_user_id时，09返回200并生成配置；10返回200且valid=false，问题包含objective、purpose、variables、collection_requirements、composition、input_recipes、evaluation缺失。04传不合法土层返回422。由此不能把10当成首页或任意分区的独立通过判定，更不能过滤其他错误后宣称整体通过。

现有完整模板可在每次修改后完整检查；自定义研究应允许后续待配置。若业务需要API逐段校验，需在共用权威校验中定义领域检查范围、依赖和未完成状态，不与UI步数绑定；本轮仅澄清与记录，没有新增step/scope参数或接口。正式保存继续全量检查，执行资格独立判断。

## 分区保存和解释面板

- 已有整份配置生成、设计检查、正式保存及兼容草稿暂存接口；没有与八分区一一对应的完成状态和分区校验合同。
- “保存本分区/自动保存”可复用整份草稿暂存，不必机械增加八个接口；但必须先明确允许暂缺的字段、分区完成判断与并发修订。正式提交继续使用完整设计检查和design-saves。
- 名称等基本字段有部分Schema限制，指标和组件有定义、单位、方法、参数说明。截图右侧“来源与依据、关联与依赖、修改后影响”并没有覆盖所有基本字段的统一元数据接口，不应让前端自行猜测科学规则。
- 不建议把作物适用范围、样本粒度、预测时间和主要输出等影响科学含义的配置藏入layout。layout可保存展示信息，但不因此获得服务端科学校验。
