# 农业预测模型发布与对外使用：一手资料及设计建议

2026-11-13。本文是设计研究，不表示已经实现模型对外发布，也不替代研究方案逐项核查。外部资料已访问官方页面；下文将资料事实、本项目现状和建议分别说明。

## 1. 成熟产品提供的可借鉴做法

| 一手依据 | 已核实事实 | 对本项目的启发与限制 |
| --- | --- | --- |
| [MLflow Model Registry](https://mlflow.org/docs/latest/registry/) 与 [Registry workflow](https://mlflow.org/docs/latest/ml/model-registry/workflow/) | 注册模型拥有多个版本；版本关联来源运行；alias 可以改指另一个版本，准确版本和 alias 均可引用。 | 区分准确科研版本与“当前推荐版本”。新建版本不能自动改变旧版本调用。MLflow 允许修改描述、标签等，不能据此宣称其所有元数据天然不可变；本项目须自行冻结科学结论与制品身份。 |
| [MLflow signatures](https://mlflow.org/docs/latest/ml/model/signatures/) | signature 声明输入、输出及推理参数；输入示例帮助调用；服务可据此验证。文档中的默认规则会忽略额外列。 | 借鉴明确合同和示例；本项目还要核对指标定义、单位、土层、时间和来源，不能照搬“忽略多余列”后让用户误以为新增因素参与了预测。 |
| [BentoML 模型管理](https://docs.bentoml.com/en/latest/build-with-bentoml/model-loading-and-management.html)、[API Service](https://docs.bentoml.com/en/latest/build-with-bentoml/services.html) 与 [输入输出类型](https://docs.bentoml.com/en/latest/build-with-bentoml/iotypes.html) | 模型存储/版本管理与 Service 中的预测逻辑分别定义；服务输入输出可用明确类型表达。 | 研究、制品、发布与服务调用分责。现有系统不必为了采用这些边界立即引入 BentoML。 |
| [BentoML 服务指标](https://docs.bentoml.com/en/latest/build-with-bentoml/observability/metrics.html) | 默认提供请求数、耗时、进行中请求等，并含服务版本等维度。 | 服务健康按准确版本观察；请求成功率不能冒充农业精度。 |
| [BentoML 异步任务](https://docs.bentoml.com/en/latest/get-started/async-task-queues.html) | 支持提交后取任务身份，再查询状态和结果；该文档同时说明其内存队列/结果会在重启时丢失。 | 只借鉴异步交互，不替换本项目已有数据库持久化、DolphinScheduler 调度和尝试租约。 |
| [Google Cloud 机器学习实践](https://docs.cloud.google.com/architecture/ml-on-gcp-best-practices) | 讨论训练与服务数据差异、随时间变化及相应监控。 | 农业侧还需按作物、地块、季节和土层检查适用性；漂移告警用于触发调查，不直接证明模型失效或授权自动升级。 |
| [Model Cards 原论文](https://arxiv.org/abs/1810.03993) | 建议随模型披露预期用途、评价程序及不同适用条件下的表现。 | 发布页必须说明“预测什么、需要什么、哪里验证过、什么情况不能用”。该论文不替本项目证明任何田间有效性。 |

结论：可借鉴 MLflow 的版本/别名/来源关系，结合 BentoML 的服务合同与观察方式；农业科学门禁仍由本平台负责。先建立自有小型发布合同和受权调用入口，不复制完整 MLOps 产品，也不把新增平台依赖当作发布能力已经完成。

## 2. 本项目已有能力与实际缺口

源码依据：[模型登记及读取](../modarchitect/runtime/store.py)、[模型和预测路由](../modarchitect/runtime/routes.py)、[预测准备](../modarchitect/runtime/service.py)、[运行合同](../modarchitect/runtime/contracts.py)、[方案发布](../modarchitect/designs.py)。

- 现有 `POST /models` 从成功的 `train` 运行登记准确制品；同一训练运行幂等登记一份模型，保留内容摘要。不是任意成功的分析、模拟运行都能登记成预测模型。
- 现有 `POST /predictions` 使用准确 `model_id`，封存预测输入和来源，继续按原制品运行。模型列表主要是 `model_id/run_id/name/model_sha256/created_at`，没有面向外部使用者的版本系列、科学模型卡、发布范围和撤回政策。
- 模型与训练运行通过工作区授权读取；因此“允许其他人调用”不是把现有内部预测地址公开，也不能让使用者拿发布者身份运行。
- “方案发布”冻结的是研究设计；“模型登记”保存的是拟合成果；“模型对外发布”还要明确适用性、预测合同、可调用主体和服务状态。三者不能共用一个含混的“已发布”。
- [当前真实采集验收](deployments/modarchitect-249/source-inputs-acceptance.md)证明了提供方采集及工程训练闭环；标签为构造数据，没有独立田间精度证据。当前资料也不足以宣称提前若干天的天气预报能力。

## 3. 建议的领域边界与正常流程

```mermaid
flowchart LR
    A[准确研究方案与输入] --> B[训练与科学评价]
    B --> C[保存准确模型制品]
    C --> D[生成发布版本并校验]
    D --> E[按授权范围开放调用]
    E --> F[使用者准备自己的输入]
    F --> G[封存准确发布版本与本次资料]
    G --> H[已有调度与 Worker 预测]
    H --> I[返回结果与准确版本]
    I --> J[后到实测形成新的评价证据]
```

建议只新增必要概念，不改写已有准确制品：

| 概念 | 职责与不变量 |
| --- | --- |
| 模型条目 | 一个稳定的农业用途，例如“马铃薯叶面积指数估计”；管理名称、所有者和版本列表，不包含不断被覆盖的训练参数。 |
| 模型发布版本 | 引用准确 `model_id`、预测合同、适用范围和评价证据；发布时冻结。相同权重若扩大适用范围或改变科学处理，也应形成新的准确发布记录。 |
| 推荐版本指向 | 可选的受控指向，例如“稳定版”；有独立修订号、操作人与变更原因。只有兼容且经核验的版本才能切换。 |
| 使用授权 | 决定谁能调用哪个范围内的版本；模型调用权不包含原始训练数据、来源凭据、模型下载或训练工作区访问权。 |

发布门禁至少包括：真实 `predict` 能力与准确执行制品可用；完整输入/输出合同与成功/失败示例；明确训练数据性质；适用性及评价证据可追溯；来源和模型使用权允许当前共享范围。工程演示允许单独标记并受限展示，不能作为“已验证农业模型”正式推广。没有通用的单一 MAE/R² 阈值可替代研究目的及预先约定的科学评价。

## 4. “更新到什么时候”必须有准确含义

| 时间信息 | 定义 | 不能混淆之处 |
| --- | --- | --- |
| 训练样本覆盖时间 | 真正参加拟合的目标观测与因素记录的覆盖范围，并保留按指标/对象的明细及缺口。 | 最大一条记录日期不等于所有指标齐备到该日。静态土壤图层不伪造为逐日新采样。 |
| 资料取得时间 | 当前准确来源快照的取得/入库时间；有提供方修订或事前可用时间时分别保留。 | 今天重新取得旧观测，不等于模型学习到了今天；未知的事前可用时间不能拿采集时间补造。 |
| 模型训练完成时间 | 本次拟合实际完成时刻。 | 登记 `created_at` 不能自动等同训练完成或资料覆盖截至。 |
| 评价覆盖时间 | 某份评价快照所用实测的覆盖范围及评价形成时刻。 | 后到实测可以新增评价，不必重训；评价改善不能覆盖旧报告或宣称参数已更新。 |
| 发布时间 | 某个准确发布版本对指定范围开放的时间。 | 重发、改名称或切换推荐版本不会改变训练覆盖。 |
| 本次预测的信息截止 | 有提前预测语义时，允许使用信息的截止点与目标提前量。 | 历史再分析天气不能冒充当时已知的未来天气。此字段由预测用途要求，不强加到所有回溯分析。 |

研究人员默认看到“模型版本、训练样本覆盖、训练完成、评价范围、发布时间”；详情再展开来源明细。缺失的历史信息显示“未记录”，不得凭发布时间推算。服务策略、监测时间属于运行信息，单独展示。

## 5. 哪些变化需要新版本

| 变化 | 建议处理 |
| --- | --- |
| 新样本重训、增量更新、重新标定、参数或特征处理改变 | 新模型制品及新发布版本；记录父版本和改变原因。即使指标名称相同，也不能覆盖旧制品。 |
| 输入指标、单位、土层、时间聚合、目标定义或预测提前量改变 | 新科学合同；通常新发布版本，若破坏兼容，不能直接替换原稳定入口。 |
| 更换数据提供方或产品修订 | 先做科学兼容验证。新取数形成新快照；若训练、处理或发布的来源合同改变，形成新版本；单次预测取得新资料不等于模型重训。 |
| 新地块/年份实测到达，仅重新评价原模型 | 新评价快照；旧模型保留；如果据此扩大公开适用范围，另建新的准确发布记录。 |
| 名称错字、联系信息等编辑性修正 | 可审计的展示修订；不改科学结论、合同或训练截止。 |
| 权限调整、暂停、恢复、撤回、推荐指向变更 | 独立管理事件，记录理由与生效时间；历史版本、预测和证据不删除、不改写。 |
| 推理环境修补 | 核对行为和制品摘要；执行包变化保留新准确运行身份及回归结果。不能仅因权重相同就静默替换历史执行环境。 |

土壤与天气联合模型尤其要避免把同一地块的一份静态土壤值重复到几十天后，当作几十个独立土壤样本。只有多地块/多季节中具备有效变异，并以与用途相符的分组或时间验证，才能声称检验了土壤因素或跨地块泛化；新增加土壤列不自动增加科学证据。

## 6. 最小对外接口建议

以下是设计草案，不是已经提供的接口。首期继续异步预测，复用实际调度；不同时推出一套未经验证的同步服务引擎。

| 操作 | 请求中必需信息 | 返回中必需信息 |
| --- | --- | --- |
| 创建模型条目 | 用途名称 | 条目身份 |
| 发布准确版本 | 已有准确模型引用、评价引用、预期用途/适用范围、授权范围、变更说明 | 版本身份、状态；来源、合同、时间从受信记录推导，不让客户端自报 |
| 查看可用模型/版本 | 分页或准确资源引用 | 必要摘要；详情另读准确输入输出、单位、必需阶段、来源准备要求、有效示例和限制 |
| 提交预测 | 路径中的准确版本；本次观测/受权快照引用；幂等键在请求头 | `prediction_id`、`status`、实际 `version_id` |
| 查询预测 | `prediction_id` | 状态；完成时返回结果与准确版本；失败时返回定位字段的业务错误 |
| 切换推荐指向或撤回 | 明确版本/目标、期望修订、原因 | 管理结果及新修订 |

示例路径可以是 `/api/v1/model-products/{id}/versions/{version}/predictions`；可选推荐入口为 `/api/v1/model-products/{id}/channels/stable/predictions`。两种调用不能含糊共用“未指定版本就用最新”。首次提交解析并封存准确版本；之后 alias 变化不影响已入队任务。重放相同幂等请求先查原任务，不能重新解析 alias 后创建另一版本的预测；同键不同请求拒绝。

预测输入沿准确合同使用。第三方指标优先提供调用者自己受权取得的快照引用，不能把任意上传数值视作已经接通的来源。若需支持“自带数值”，须另有明确允许的来源/科学合同与验证方式，不绕过当前来源门禁。输出只含预测所需结果、单位和准确版本，不泄露训练表、发布者私有快照、执行凭据或内部调度参数。

认证得到使用者身份；发布授权授予有限的模型调用权；本次输入与结果仍归使用者权限范围。实现时需单独提供受授权的准确模型读取能力，不能借用发布者工作区身份绕过 RLS。撤回后新请求包括准确旧版本请求均拒绝，不能悄悄改用其他版本；已排队与执行中的请求按明确政策取消/阻止结果发布，保留审计记录。读取已有结果的政策也需独立约定。

## 7. 建议的最小验收

1. 同一准确发布版本在推荐切换前后，使用相同封存输入得到可核对结果；旧幂等请求仍指向原任务与原版本。
2. 不兼容合同不能切换到旧稳定入口；多余/缺失指标、错单位/土层、不可用来源、越权快照有明确拒绝。
3. 被授权使用者可以预测但看不到训练私有数据；撤销权限、撤回版本、越权查询预测均按政策处理。
4. 新评价不改旧模型与旧评价；新资料不自行改变训练截止；静态土壤与重复日值不虚增独立样本。
5. 分开验收工程闭环与科学证据。先完成土壤+天气方案的准确配置、真实取数和可复跑结果；正式农业用途发布另需相符的真实目标、划分及独立评价。
6. 运维记录准确版本的调用量、延迟、失败、来源缺口；实测到达后追加科学误差评价。监测告警先产生待复核事项，训练候选、评估、采用与推荐切换仍保留各自门禁。

实施顺序建议：先修准确方案与输入清单，再做土壤+天气的可复跑研究和真实/工程证据标识，然后新增最小发布合同、受限异步调用与撤回。已有组件合同、来源快照和实际调度继续复用。
