# 可替换输入来源的架构约定

2026-11-12。首批来源框架和第三方采集已实现部署；证据见[249 验收](deployments/modarchitect-249/source-inputs-acceptance.md)。本文件中的完整科研能力分期交付，不以架构约定代替实际接通证据。既有准确来源定义及运行摘要保留。

已结合用户补充的农业科研与数学建模建议复核；逐项事实、采用/调整决定及一手依据见[农业输入与组件复核](agricultural-input-design-review.md)。来源接通与科学可用于研究分别验收。

## 目标与当前事实

研究人员选择研究指标；平台负责准确来源及获取规则。来源的更换不能要求研究算法认识不同厂商，也不能让历史方案或模型在不知情时换源。

改造前已检查的入口、合同、调用方和测试基线：

- `system_inputs.py` 目前同时构建目录、生成输入绑定、核验定义和封存来源。固定目录正确限制了 33 项准确绑定，但取数通道目前只有 4 项人工录入。
- `CollectionRequirement` 已表达变量、方法、单位尺度和准确来源；`CatalogBinding` 已包含版本、摘要、取数属性及值性质。继续采用这些合同，不另建一套相同含义的字段。
- `runtime/preparation.py` 的 `prepare_observations` 与 `ResearchRuntime.save_plan/train/predict/check_execution` 已共用来源校验；计算 Worker 消费封存输入。这是保留的主链。
- `_entry` 当前由来源组件 code 推导 `source_system`，`validate_input_bindings` 在当前 `input_catalog()` 中查绑定，并调用当前 `configure_input` 对照方法。若将来直接替换当前列表，历史绑定会无法解析；若直接追加同变量策略，当前输入 key 又可能重复。这是扩展前需解决的耦合点，并非宣称现有单一策略已发生碰撞。
- 当前观测表仅表示地块种植季日值，不能容纳全部点位、单株、报告覆盖区和传感器时序。统一接入不等于把所有来源降成这种表。

## 一、领域边界

下列职责分别表达，尽量复用现有合同；“分开”不要求每个概念都建一张表或一个服务。

| 概念 | 决定什么 | 不应决定什么 |
| --- | --- | --- |
| 指标定义 | 科学含义、规范单位、允许范围、版本 | 提供方 URL、设备账号、请求协议 |
| 来源定义 | 提供方/产品、原始字段、空间与时间支撑、方法、值性质和允许属性 | 当前是否采用、当次数据是否齐备 |
| 来源采用策略 | 某指标当前允许用于新研究的准确来源及适用范围 | 自动改写已保存绑定 |
| 来源绑定 | 一份方案采用的准确来源版本、摘要、属性和方法 | 客户端覆盖来源或选择任意地址 |
| 接入适配器 | 怎样读取该准确来源，以及如何按准确转换方法产生标准记录 | 训练目标资格、研究业务规则、自动换源 |
| 来源快照 | 本次实际记录、原始证据、转换版本及授权依据 | 可随提供方更新覆盖的“最新缓存” |
| 研究输入装配 | 按准确方案选择快照、对齐科学对象与时间、检查缺口、封存计算输入 | 下载实现、设备登录、静默补数 |

四类来源是目录分类；HTTP、WCS、文件、消息订阅和业务查询是接入协议；实时、定期和人工提交是触发方式。三个维度独立，不能用“四类”枚举决定所有获取行为，也不能因接入协议相同而认为科学来源相同。

上游模型输出继续走成果合同及派生变量链路，不能通过来源适配器重标成独立实测。

## 二、采用的设计方式

采用**端口与适配器**作为依赖边界，内部使用**适配器模式、策略模式和依赖注入**，以组合表达差异。版本化来源及不可变快照保证历史解释。

1. **端口与适配器 / 适配器模式。** 研究流程面对获取合同；Open-Meteo、SoilGrids WCS 和未来业务/设备连接分别实现该合同。厂商字段、认证和协议留在适配器内部。
2. **策略模式。** 通过获准的准确绑定查找已登记接入实现；不按类别写一串 `if source == ...`，不让算法或页面选 URL。注册表仅做准确匹配和生命周期检查，没有匹配就拒绝。
3. **依赖注入。** 应用/采集 Worker 入口装配注册表、受限客户端和持久化。领域规则不读部署环境、连接数据库或自己创建 HTTP 会话；测试替换传输依赖，通过同一正常入口验证。
4. **组合优先。** 适配器组合协议客户端和确定性转换函数。没有 `BaseSource` 多层继承，也不要求人工、影像和传感器实现无意义的 `connect/login/download/subscribe/train` 方法。
5. **不可变快照。** 研究采用快照，计算 Worker 不联网重新取得“最新数据”。提供方修订、人工纠错或分析重跑形成新快照，旧快照保持原身份与证据。

暂不引入独立插件市场、通用插件扫描、任意脚本执行、微服务拆分、通用工作流引擎或新的抽象 Repository 层。当前两个外部提供方已经构成真实的适配差异，足以建立一个小端口；其他来源在实际接入时按合同扩展。

## 三、共同获取合同

首批实际接口为 `SourceAdapter.acquire(entry, binding, request) -> SourceSnapshot`：entry/binding 由受权准备冻结，固定客户端和资源预算在构造时注入，执行权由采集编排核对。缺数或不相容明确失败，批次完整成功后才发布快照。未来人工等待及部分缺口需要时再增加版本化 Outcome，不预建空字段。下表是跨来源扩展的职责约定；首批不强制为每一项建立独立类。

| 输入/输出 | 必要含义 |
| --- | --- |
| `AcquisitionRequest` | 服务端已解析的准确来源绑定、授权研究范围、必要取数属性、时间范围及知识截止条件 |
| `AcquisitionContext` | 受信主体、执行权、限额/期限、取消检查和已注入的受限连接；不由公开请求填入凭据 |
| `AcquisitionOutcome` | 本次取得的标准记录与原始证据，以及明确缺口；依赖失联、权限拒绝、合同不匹配等失败有独立错误类型 |

接口不生成虚拟默认值，不写研究结果，不创建人工待办，不在缺数据时自动调用第二来源。协议传输与确定性转换分开，单位、空间/时间含义仍由该版本的方法约束。共用门禁只核对共同不变量，不重新实现每个提供方的科学算法。

人工输入的 `acquire` 读取已经提交并符合相应资格的记录；没有记录就返回缺口，不能等待人填表。表单提交、审核和纠错是独立采集入口。物联网适配器读取已归档时序；持续 MQTT 订阅由接入进程负责，不能放在一次研究的读取方法中。平台分析读取已形成的报告/影像产品；重新计算 NDVI 是可追溯的分析任务，不能隐藏在读取中。

### 标准记录与来源快照

标准记录至少能够解释：准确指标与来源、规范值及性质、观察单元、实际空间支撑、有效时间、记录修订和质量。来源快照补充原始资料及摘要、准确接入与转换制品、取得时刻、提供方生成/修订信息、授权/许可依据。

这些信息按归属放在快照头、记录或原始制品中，不能每行重复整个合同；研究请求只引用快照。原始系统没有修订号时使用明确的内容版本，不伪造供应商版本。原文和规范值都留存，使纯转换能够独立复跑。

时间至少区分观察/生效时间、提供方可用时间和本系统取得时间。缺可用时间时可以做明确标注的回溯研究，但不能宣称通过了“当时已知”的预测回测门禁。静态土壤多日引用同一来源记录；新日期行不会增加独立样本。快照不能把估计值改成实测，也不能把点位值改成地块平均。

已有地块日值 `ObservationTable` 是计算输入的一种形式，放在装配之后。无法适配其科学单元的输入明确拒绝；以后增加点位/单株/土层计算输入时扩展对应合同，不能先把信息压平丢失。

## 四、四类来源的实际差异

| 来源类别 | 获取对象 | 特有规则 | 可替换部分 |
| --- | --- | --- | --- |
| 人工采集 | 采集记录的准确修订及证据 | 样株/点位、方法、人员/仪器、审核资格；纠错形成新修订 | 表单系统、文件导入或移动端接入；测量方法改变需新合同 |
| 第三方平台 | 已指定产品的真实响应 | 产品版本、日期/网格、单位转换、许可；土壤 WCS 覆盖与无效值门禁 | 厂商或协议；厂商变化不能只换 URL |
| 平台分析记录 | 准确报告、影像与分析结果 | 空间覆盖、日期、算法/模型版本、质量及成果摘要；报告覆盖区不冒充点位 | 报告存储/API；更换算法需新成果与来源版本 |
| 物联网平台 | 设备、点位/土层的时序记录 | 设备归属、校准、时区、采样频率、质量、重复/乱序/迟到和日聚合方法 | 平台、协议及设备接入；变更设备/聚合方法按准确合同处理 |

目前人工测量证据校验、平台分析绑定和物联网绑定都未完善。本架构不授予它们新的来源资格；按真实接入验收逐项采用。

## 五、更换来源的规则

来源存在、获准采用、接入可用、当次数据齐备及可参与某次研究是独立事实，不维护彼此可矛盾的一组手填布尔值。

| 变化场景 | 处理方式 | 历史及模型行为 |
| --- | --- | --- |
| 同提供方凭据轮换/等价端点变动 | 更新受控连接配置；不改变科学内容，接入实现有实际变化时记录新制品 | 旧快照保持原内容，可独立重算 |
| 同一来源 HTTP 改 WCS 或接入实现修复 | 只有科学含义完全相容且经正反例验收，才能采用新的接入实现版本 | 原快照保留原实现摘要；不通过联网重取替换旧值 |
| Open-Meteo 换成另一天气提供方 | 新增准确来源定义及采用策略版本，显式迁移草稿并检查单位、日界、产品、空间支撑和方法 | 已发布方案继续引用原来源；旧模型不自动接受新源，默认形成新研究/候选模型再评价 |
| 24 小时均温换成极值均温、报告区 NDVI 换点位 NDVI | 根据科学差异新增准确方法/来源，必要时新增指标定义版本；不能当作纯协议变更 | 历史解释保持；必须重新进行适配与研究验收 |
| 人工纠错/影像重处理/提供方修订 | 新记录修订与快照，通过明确的数据采用产生新运行 | 旧运行及训练来源不覆盖；预测形成当次来源清单 |
| 来源停用或授权撤销 | 区分禁止新采用、禁止新取数和受控的历史证据保留；启动时重核执行资格 | 可以解释历史不等于可以重新读取或执行；不自动改用备用源 |

**当前采用解析与历史解析必须分开。** 新设计通过 `adopted_source(variable, scope)` 取得当前批准来源；历史读取通过 `resolve_binding(code, version, sha256)` 取得准确已冻结定义，执行资格再独立核查。不能用当前目录的第一项或 `latest` 解释历史。

当前来源 code 中即使含有厂商名，也继续是准确历史身份。它不作为研究服务分支的条件。接入注册表以准确来源合同及部署采用记录映射到准确实现；相同指标的当前入口可以稳定，但其选择必须明确且唯一。若未来允许同一范围同时存在多种来源，就新增明确选择合同，不允许重复 key 后取第一项。

## 六、应用流程与执行边界

```mermaid
flowchart LR
    Design[研究指标与准确来源绑定] --> Request[授权范围与采集需求]
    Request --> Acquire[采集编排]
    Acquire --> Adapter[按准确登记选择适配器]
    Adapter --> External[第三方或业务数据系统]
    External --> Snapshot[原始证据与标准记录快照]
    Snapshot --> Prepare[研究输入装配与统一门禁]
    Prepare --> Seal[封存本次输入]
    Seal --> Compute[计算 Worker]
    Compute --> Model[成果与模型保留来源引用]
```

采集编排与研究计算是两个阶段。任何预检只读当前资料，不触发联网下载、分析计算或采集待办。草稿可以表达资料缺口，实际启动须满足输入合同。

第三方采集采用明确的异步采集资源：API 短事务创建请求，DolphinScheduler 实际调度采集 Worker；Worker 领取封存的来源绑定、范围和限额后取数，服务端按执行权校验回传并保存快照。计算 Worker 后续只读已封存标准输入。允许同一 Worker 部署承载这两个入口，但不能把取数副作用藏在研究校验函数中。

已有 `research_runs` 强关联方案版本，`research_dispatch_queue` 又引用研究运行，不能直接把采集假装成一种研究训练。新增采集资源可用自身待投递状态作为持久投递依据；调度客户端按实际共性提取，保留各自领取、执行权、结果回传和对账规则，不再另造一套任务框架。

关键失败规则：

- 创建采集前核对对象授权、准确绑定及调用资格；返回后和研究启动时再次核对适用授权与来源采用状态。
- 网络等待不持有数据库事务。重试有界，尊重限流；相同请求幂等键与相同封存条件复用原采集身份。主动重新抓取必须创建新请求。
- 调度回执丢失保持待对账，不能盲目重投。领取、重试和取消均有执行尝试身份，迟到结果不得覆盖已取消或已完成的采集。
- 部分来源成功可以保留成功快照及明确缺口；未经完整输入门禁不能启动依赖它们的研究。预检不静默删行、换站、填均值或替换来源。
- 受控缓存按准确来源、属性、空间/时间、修订及转换身份命中。数据内容缓存不能替代工作区/企业授权和限期许可；撤权后不得绕过门禁返回缓存。
- 采集失败、资料不足和输入不相容分别有可判断原因；只有临时性失联/限流可按声明重试，权限或合同错误不自动重试。

## 七、API 与持久化边界

采用已有方案、实例、授权范围和观测修订资源引用；没有现成资源时只补必要的最小合同，不复制整份来源定义到每次请求。

拟定公开接口为 `POST /workspace/plans/{design_id}/input-acquisitions`，提交准确草稿修订、研究范围及必要日期；来源从方案解析，不由请求覆盖。返回 202 与 `acquisition_id`。查询采集只返回实际状态、已形成快照引用及失败/缺口；快照读取接口返回研究需要的标准记录，原始证据受权单独读取。路径与 DTO 在实施前核对 OpenAPI 和实际调用方，不把本记录当作已发布 API。

企业范围的地块、点位及坐标从受权业务资源解析；个人工作区声明的参考点只能取得本人的参考研究资料，不能作为企业选地资格。两种范围使用明确的不同合同，不接受客户端自报企业归属。

当次请求只补必要的快照资源引用，不在旧计算表里直接增加来源、质量或支撑字段。现有回归组件严格要求表的准确键集合；装配时按准确端口投影，丰富证据留在来源资源和运行来源清单，需消费新元数据的组件另发版本。历史空引用的序列化、请求幂等摘要和制品输入均保持原样，不能仅凭字段可选就认定兼容。保存、预检、训练和预测都从持久化层按主体解析引用，再将受信快照传给同一封存规则；不信任客户端提供的快照摘要、来源标志或数值。

第三方列必须逐一匹配快照中的准确变量、属性、对象、时间及值。允许使用符合范围的子集，禁止同一对象日期出现冲突来源后任意挑一条。标准记录的新增、删除、替换通过明确选择/新快照完成，不修改提供方证据。来源、方法、原文和摘要随运行与模型保留，预测不覆盖训练证据。

新增持久化只承担采集执行记录和不可变来源快照，按实际查询需要决定是否分表；授权复用现有可信主体与强制 RLS，必要约束落到数据库。原始大制品可分离存储，但必须有摘要、权限、留存和清理边界，不能仅保存会失效的临时 URL。

## 八、目录及依赖约定

首批按实际职责保持紧凑，不为每个动作建文件：

```text
modarchitect/
  system_inputs.py             准确目录/采用解析、来源资格及封存规则
  input_sources/
    __init__.py                仅公共声明
    contracts.py               获取请求、标准记录、快照及错误类型
    service.py                 采集应用流程与准确适配器注册
    weather.py                 Open-Meteo 客户端与纯转换函数
    soil.py                    SoilGrids WCS 客户端与纯转换函数
  persistence/source_store.py  采集执行、快照、幂等和主体隔离
  runtime/                     受权解析快照、原研究调度和封存计算
```

上述结构已落地，并按实际职责增加 `transport.py`（有界公共通信）、`routes.py`（协议）、`worker.py`（领取与回传）。接入更多来源时优先放入其领域模块；一个提供方需要多种独立变化时再拆通信与转换，不预建空的人工/影像/设备实现。

依赖方向：API/采集 Worker → 采集应用流程 → 获取合同；提供方适配器实现该合同；研究流程 → 准确目录规则和受信快照。`system_inputs` 不导入路由/数据库/具体提供方；算法不导入接入客户端；HTTP 客户端、凭据和注册装配只在运行入口出现。普通计算组件不因自助上传而获得访问业务系统的凭据或网络权限。

## 九、先验收再称为可替换

| 场景 | 应有结果 |
| --- | --- |
| 天气换厂商 | 仅新增适配器、来源定义、采用记录及对应验收；研究输入装配与算法不加厂商分支 |
| 同提供方换协议 | 科学合同相同才复用绑定；记录新实现制品，旧原文仍按旧实现复算 |
| 同一指标跨四类来源 | 只在科学定义、观察单元和明确适配相容时采用；来源性质及实测标签门禁保持 |
| 当前来源升级 | 新研究取新采用版本；旧方案准确解析旧版本；执行时独立检查停用/撤权 |
| 合并实测与提供方记录 | 全对象、时间和单位严格匹配，少数据给缺口；篡改值、错土层/点位及冲突修订拒绝 |
| 时间回测 | 只接受满足该次知识截止规则的记录；事后历史下载不能冒充当时已知资料 |
| 重放、并发、取消、迟到结果 | 不生成冲突快照、不覆盖旧来源、不重复投递不明任务、不跨主体读写 |
| 正式来源接通 | 提供方真实正反例、隔离库约束和真实调度通过，不能仅凭替身、HTTP 200 或目录 available 标志 |

首批第三方还须验证：天气产品实际延迟/24 小时/单位/质量；土壤 WCS 原生像元 CRS/transform、准确图层土层及单位、有效覆盖和 NoData。海域零值无 NoData 的处理在充分验收前保持阻断，不能全零删掉或全部当有效。详见[一手调查](third-party-provider-research.md)。

实施顺序：先整理准确绑定解析与当前采用边界；再落获取合同、不可变快照及统一装配门禁；以天气和土壤两个适配器验证替换边界；最后接四类各自实际系统。每一步都保留旧人工与合成方案、批准档案、模型及训练/预测回归。第三方实施记录见[取数接入计划](third-party-input-acquisition.md)。

## 十、农业科研语义补充

以下与来源替换共同实施，准确归属、当前实现差距及正反例以[农业输入与组件复核](agricultural-input-design-review.md)为准：

1. 科学分类用于按研究问题检索，四类来源用于接入管理，节点用途由准确组件请求推导。三者独立，不用一个 role 或 category 同时表达。沿用 1.5 的 InputUsage，不另存第二份因素/目标关系。
2. 指标定义、准确来源和实际记录分别保存科学事实。值性质、实际支撑、设备及静态/事件等产品行为不能永久绑定全局指标。同名指标也需核对测量对象与方法。
3. unit_kind 继续表达观察单元类型；实际空间范围、土层区间、时间范围、统计轴和聚合方法另有准确依据。单株、样方、报告区、网格及地块不能通过改枚举自动相容。
4. 复用 ScientificUnit/StudyContext 及独立试验单元合同，把实际记录与上下文校验接入运行。声明层级不等于日值适配器已支持所有样株；不能满足时明确拒绝。
5. 来源规范化与研究处理分开。研究按目标日期/提前量建立样本、封存划分，再在对应训练范围拟合插补、归一化、变量选择等状态；预测复用准确状态。预检检查来源可用时间与整个派生路径，不能信任手填“无泄漏”标志。
6. 平台产品、处理活动、派生指标通过准确谱系关联，保持与研究图一致。器件校准、人工测量证据、数据质量和误差按对应记录/方法归属；未知不填 0，不要求所有组件输出同一种不确定性。
7. 静态数据展开、同株多日和同小区多株不会增加独立重复；单对象常量因素还须通过模型可辨识性门禁。数据已取得不保证所选数学模型有可估计的参数。

第一批只实现天气和土壤接入所必需的这些合同与门禁。完整表型本体、全套试验管理、传感器平台及数据同化按真实组件需要增量交付，不扩为六个独立服务。
