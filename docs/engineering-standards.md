# 架构与编码质量规范

2026-11-11 核对。适用于模型设计器、研究服务、计算组件和执行接入的新增功能、重构及评审。目标是让方法、数据来源和执行方式可以独立演进，并保留既有方案与组件的准确解释。

## 职责与依赖

API 的 request 和 response 只承载完成当前操作必需的最小业务单元。已有资源可复用时不重复包装；不回传请求已知值、内部调度配置、重复布尔能力或仅供排版的标题/颜色/固定步骤。需要调用方判断的权限、状态和错误保持明确且类型化。输入增删和可执行判断按[研究平台规则](platform-rules.md)，只读检查与实际启动共用权威校验。

一次功能设计先沿实际入口、调用方、契约、存储或 Worker 画出依赖，写明每个模块负责的决定。`GLOSSARY.md` 继续作为领域术语入口。当前项目的职责按下表判断，实际拆分随功能需求落地。

| 职责 | 对调用方提供的能力 | 依赖和副作用 |
| --- | --- | --- |
| 数据与行为契约 | 变量、研究方案、组件端口、版本和成果的准确含义，结构与引用约束 | 保持可独立使用。核心契约导入时应能在 API、数据库及调度服务均未启动的环境工作。 |
| 研究规则与计算 | 方案有效性、变量角色、成果来源、科学配对和版本采用等决定 | 共享规则集中维护。纯计算以显式输入产生结果。外部身份和数据通过受信接入提供。 |
| 应用流程 | 保存、发布、启动、取消、重试等完整动作 | 编排研究规则、授权证据和持久化，明确状态转换、事务和失败恢复。 |
| API、页面和 Worker 入口 | 解析请求、获取可信身份、调用流程、返回状态或执行结果 | 页面按合同显示配置和错误。服务端作权威校验。Worker 按封存输入执行并回传。 |
| 存储和外部接入 | 数据库读写、业务数据访问、制品存取及 DolphinScheduler 通信 | 封装查询、网络、进程和资源释放。向调用方返回明确的结果或失败类型。 |
| 组件与执行协议 | 版本化清单、输入输出、制品身份及独立复跑 | 遵循 [组件架构约束](../coding/model-designer-migration.md#组件架构约束)。按已登记制品执行。 |

依赖通过入口装配或显式参数传递。调整模块时沿全部调用方核对身份、事务和版本语义。具有相同业务含义的规则只维护一份权威实现，API、Worker 与界面复用其合同及结果。相似代码若来源、单位或失败语义不同，先写清差异，再决定是否提取共用逻辑。

## 模块与抽象的判定

1. **按变化原因组织。** 一个模块能说明自己的职责和调用方。需要因多个独立原因反复修改时，沿真实职责拆分。同一职责的紧密相关函数可以放在同一文件，文件数和行数结合阅读与修改成本判断。
2. **接口表达完整约定。** 明确输入类型、单位、版本、前置条件、返回结果、错误、幂等及资源归属。调用方通过接口使用能力，内部数据库结构、传输细节和算法库由实现管理。
3. **以真实变化决定抽象。** 提取共用规则前核对实际调用方。需要替换或隔离测试的依赖可以定义小接口。无状态逻辑使用清晰函数，有共同状态、资源生命周期或不变量时使用类。继承须保留调用方依赖的行为，组合按实际职责建立。
4. **抽象产生可检查的收益。** 同一规则修改集中在权威模块。替换外部实现时，调用方的领域含义稳定。公共接口能直接用于正常入口和行为测试。新增转发层要承担实际校验、策略或资源管理职责。
5. **选择显式数据流。** 配置、业务上下文和外部连接有明确来源。模块导入以声明类型、函数和必要公共接口为主，连接和任务启动在应用生命周期内完成。异常保留可定位信息，部分失败仍维持已声明的状态约束。
6. **泛化保留语义。** 新模型沿版本化合同声明变量角色、成果和适用性，已有可表达的规则通过元数据进入共用校验。算法特有的科学判断由对应实现负责。用户组件与内置组件执行同一套合同和制品验收。

## 用改造场景验证基础框架

下列是评审新设计时的检查场景。先在功能设计里列出预计修改位置，实施后解释实际差异。对现有问题的判断附调用方、可触发条件及影响，待核实的扩展需求保留为假设。

| 改造场景 | 良好结构应呈现的结果 | 验证方法 |
| --- | --- | --- |
| 增加同协议的模型组件 | 实现和登记集中在组件与目录接入，设计器按合同显示专属参数和成果，通用执行沿用已声明协议 | 独立组件正反例、方案加入与执行、既有组件回归。检查新增的算法名称分支有无重复科学规则。 |
| 更换农业数据来源 | 新接入产生带来源、单位、观察单元和可用时间的标准输入，研究判断沿用权威模块 | 用合法、缺失、异单位、跨对象和事后到达数据检查适配与配对结果。 |
| 单目标扩展为多目标 | 每个目标有自己的定义、成果及评价，模型支持的数量和组合由合同表达 | 通过正常配置与运行入口验证不同单位的双目标、部分缺测及准确输出列。 |
| 增加组件修订 | 新设计读取获准版本，历史方案仍能解释其冻结引用和准确制品 | 历史样例往返、摘要篡改拒绝、停用和采用状态检查。 |
| 调整保存或发布实现 | 修订冲突、重复请求、授权及冻结版本的外部行为有准确约定 | 从 API 入口验证重复写、并发修订和发布读回。涉及存储语义时使用已确认的隔离数据库。 |
| 接入或替换调度实现 | 研究运行身份、封存输入及成果归属稳定，提交和恢复依照外部系统的真实回执处理 | 按 [真实调度验收](../coding/model-designer-dolphin-acceptance.md) 验证超时重投、取消、失联和迟到结果。 |

当前代码可作为后续改造的检查起点。`ResearchDesigns` 编排草稿及发布，`DesignStore` 管理持久化，边界已可辨认。`input_bindings.py` 中仍有按组件代码处理语义的分支，目录由首批合同装配。扩展组件接入时，应核对哪些分支能由版本化声明共用，哪些属于算法专属判断。这些是结构检查点，具体改动及验收按对应功能设计执行。 [应用流程](../modarchitect/designs.py) · [持久化](../modarchitect/persistence/design_store.py) · [输入绑定](../modarchitect/contracts/research/input_bindings.py) · [目录](../modarchitect/catalog.py)

## 每次交付的质量证据

涉及数据来源接入或替换时，先按[可替换输入来源的架构约定](../coding/input-source-architecture.md)检查边界：当前采用与准确历史解析分开；具体获取实现按准确登记注入；预检不取数；计算只消费封存标准输入。采用适配器、策略与组合，不把提供方分支加入研究算法，不以统一接口抹平人工、影像、网格与传感器的科学差异。来源变更必须用旧方案/旧模型及换源场景验收，不能只验证新提供方请求成功。

农业科学元数据按[输入与组件复核](../coding/agricultural-input-design-review.md)明确字段归属及生产/消费方。优先复用节点用途、协议、试验单元和来源性质，禁止并行保存重复角色、重复深度或客户端自报“无泄漏”。研究处理须保留划分及拟合范围；新证据向旧组件装配时保持准确端口合同。完整标准的概念参照不等于当前实现已经符合该标准。

- **设计能对应实现。** 功能记录写清入口、权威规则、状态变化、依赖、准确版本、兼容行为及可观察验收。跨模块改动说明正常与失败路径，指明涉及的所有调用方。
- **重构有行为依据。** 先核对现有公开入口、测试及历史样例，再分步调整。复现缺陷或验证新行为时，用独立来源的预期结果。测试尽量通过稳定接口观察结果，保留能发现实际回归的用例。
- **验证与改动匹配。** 按 Python 规范完成相关行为测试和文件头检查，执行项目已有的适用静态检查。涉及打包、数据库、外部授权、浏览器或调度时完成相应验收，记录实际环境与跳过项。静态检查通过、合成计算正确、业务联验成功各自提供证据。
- **评审说明具体后果。** 依据设计和合同检查变更，对问题说明触发条件、预期、实际行为、位置、影响及修复后的验证。跨模块问题同时检查生产方和消费方，核对已有机制能否防止或修复该情况。
- **简化检查落在本次改动。** 复查命名、重复逻辑、嵌套、多重职责和纯转发抽象。修改后重跑受影响的行为验证，确认公开接口和准确制品语义符合设计。
- **交接可继续执行。** 提供变更位置、准确版本、真实命令、结果和待验证条件。遇到重复性缺陷，将有效复现加入已有回归，并把必要约定更新到权威规则或检查入口。

稳定且可自动检查的依赖方向、类型和静态规则，随涉及这些约束的功能改造纳入项目配置与现有验收入口。新增工具先核对兼容性并在 `pyproject.toml` 声明。每项功能采用与风险和变化范围相符的检查，已有会话授权及项目技术边界继续适用。
