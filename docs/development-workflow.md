# 团队协作与开发工作流

## 每项任务

1. 从实际入口沿调用链追到契约、持久化或 Worker。给出源码依据和会影响判断的假设。跨模块方案用简短的流程图或伪代码明确正常路径和关键失败路径。
2. 用可观察结果定义验收。新增或扩展功能先维护 `coding/` 中对应设计记录。复用现有规则和回归。能改变验收结论的行为缺口，用最小测试覆盖。
3. 实现后重跑对应场景，检查调用方和实际差异。交接附版本、变更位置、可复跑命令、结果和待验证项。反复遇到的故障或约束写回现有文档。

主代理负责范围、整合与验收。会话允许且已授权时，独立调查、实现或审查可委派。委派提供工作目录、基线、可写文件和验收方式。共享契约、迁移及未隔离的测试资源由主代理安排顺序。

新增能力和重构按 [架构与编码质量规范](engineering-standards.md) 检查模块职责、依赖及可改造性。该文档保留 Anthropic 官方资料、Karpathy 社区指南、Ousterhout、Fowler 和 Matt Pocock 技能的来源及适用范围。

## Python 规范

| 何时 | 读取与执行 |
|---|---|
| 需求、设计、实现或评审 | 读取 `python-project-standards` 与 `karpathy-guidelines`。设计写明入口、状态、依赖方向、历史兼容及最小验收。已有行为优先沿用。 |
| 涉及 API、数据库或长任务 | 读 Python 规范的 `references/backend.md`，核对身份、短事务、幂等、投递、取消、重试和资源释放。迁移按模型元数据和目标隔离库验证。 |
| 修改自有 Python 源码 | 读 `references/python-style.md`。文件头使用实际创建时间、作者与文件名，模块及函数用中文说明。完成时用当前 Python 运行该技能目录的 `scripts/check_python_headers.py`，传入全部本次自有新增或修改的 Python 文件，并运行对应行为测试。 |

技能优先从 Codex 的可用技能目录定位。本机 `python-project-standards` 与 `karpathy-guidelines` 位于 `E:/CodexData/home/skills/`。某项技能缺失时按本项目可读规范推进可完成的工作，并记录限制。

## Matt Pocock 技能的使用时机

按任务选用，在执行前读取对应 `SKILL.md`。任务与领域配置见 [Agent skills](../AGENTS.md#agent-skills)。

| 场景 | 技能与结果 |
|---|---|
| 需求或领域边界有实际歧义 | `grilling` 与 `domain-modeling`，或可用的 `grill-with-docs`。先核对代码证据，再明确需要人判断的取舍。已确认术语和难逆决策进入术语表及适用 ADR。 |
| 核实外部契约或调整模块边界 | `research` 核对一手来源，`codebase-design` 检查模块接口、共用规则及测试边界，并按工程规范中的改造场景核对修改范围。需要实际观察才能决策时，用 `prototype` 验证一个问题并记录证据。 |
| 跨多个会话实施 | 可用时使用 `to-spec`、`to-tickets` 和 `implement`。功能设计以 `coding/` 为准，任务记录引用对应设计并写明前置任务和验收。涉及并行实现时遵循当前会话的授权及隔离条件。 |
| 关键行为或难复现缺陷 | `tdd` 用最小失败用例推动实现，`diagnosing-bugs` 先形成可复跑的失败反馈，再区分假设、修复并回归。 |
| 改动复核与交付 | `code-review` 对照需求和项目规范复核差异，附位置、触发条件和影响。需要编写 PR 时使用 `pr`。维护代理规则时使用 `writing-for-agents`。 |
| 跨工作目录交接或复盘 | 可用时用 `handoff` 保存目标、证据和下一步。用 `retro` 把反复出现的问题转化为可执行检查或现有规范的更新。 |
